# 2048 게임 검증(Review) 작업 지침

## 배경
`my-blog` 프로젝트의 Plan → Build → Review → Embed 사이클 중 지금은 **Review** 단계다. 계획은 `C:\Users\SNOO\Desktop\my-blog\apps\2048\spec.md`, 구현은 `C:\Users\SNOO\Desktop\my-blog\apps\2048\index.html`, `style.css`, `game.js`에 있다 (Build 서브에이전트가 작성함). 너는 Build를 작성한 서브에이전트와 별개의 독립적인 검토자다.

## 해야 할 일
1. `spec.md`를 읽고, 구현된 3개 파일(`index.html`, `style.css`, `game.js`)의 코드를 직접 읽어라.
2. Claude Browser 도구로 실제 브라우저에서 게임을 실행하고 다음을 확인해라.
   - 페이지 로드시 타일 2개가 생성되는지.
   - 방향키(상하좌우) 각각으로 타일이 밀리고, 같은 숫자끼리 병합되며 점수가 올라가는지.
   - 같은 턴에 병합된 타일이 다시 병합되지 않는지 (예: [2,2,4]를 왼쪽으로 밀면 [4,4]가 되어야지 [8]이 되면 안 됨).
   - 이동으로 실제 변화가 없을 때(예: 이미 벽에 붙어 그 방향으로 더 이상 못 미는 상황) 새 타일이 생기지 않는지.
   - 점수(SCORE)와 최고 점수(BEST)가 정상적으로 갱신되고, 페이지를 새로고침해도 BEST가 유지되는지 (localStorage).
   - "재시작(New Game)" 버튼을 누르면 점수가 0으로 초기화되고 보드가 리셋되는지.
   - 2048 타일이 만들어지면 승리 오버레이가 뜨는지 (직접 2048까지 플레이하기 어렵다면, 개발자 콘솔이나 임시 코드 수정 없이 코드 리딩으로 로직이 맞는지 검증하는 것으로 대체 가능 — 단, 실제로 코드를 변경하지는 말 것).
   - 모바일 폭(375px)으로 리사이즈했을 때 보드가 화면을 벗어나거나 잘리지 않는지, 가로 스크롤이 생기지 않는지.
   - 브라우저 콘솔에 에러가 없는지.
3. 코드 자체도 검토해라: spec.md의 설계(특히 4방향 이동을 하나의 로직으로 통일하는 부분, 재병합 방지 로직)를 실제로 따르고 있는지, 명백한 버그나 엣지 케이스 누락이 없는지.
4. 검증 결과를 `C:\Users\SNOO\Desktop\my-blog\apps\2048\review.md`에 정리해서 작성해라. 발견한 문제(있다면)와 각 항목의 통과/실패 여부를 명시할 것.
5. **문제를 발견했다면 직접 수정해라** (`index.html`/`style.css`/`game.js` 범위 내에서). 수정 후 다시 브라우저에서 확인해서 고쳐졌는지 검증하고, `review.md`에 어떤 문제를 어떻게 고쳤는지도 기록해라.

## 제약
- `/apps/2048/` 폴더 안의 `index.html`, `style.css`, `game.js`, 그리고 새로 작성할 `review.md`만 수정/생성한다.
- 프로젝트의 다른 파일(`build.js`, `lib/`, `public/`, `posts/`, 루트 `index.html`, `spec.md`, 지침 파일들)은 건드리지 않는다.
- 프리뷰 서버(포트 5173)는 이미 실행 중일 수 있으니, 새 서버를 띄워야 한다면 반드시 다른 포트를 쓰거나 기존 서버를 건드리지 말 것. 절대 `taskkill`처럼 다른 프로세스까지 죽일 수 있는 광범위한 명령을 쓰지 말 것 — 반드시 이 세션에서 직접 띄운 서버만, 정상적인 방법(예: 해당 서버의 serverId로 preview_stop)으로 종료할 것.

## 완료 후
`review.md`의 핵심 내용(통과 항목, 발견/수정한 문제)을 요약해서 보고할 것.
